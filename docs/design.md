# libbdf の設計メモ

bdf（Go の参照実装と TypeScript のビューア）とは別に、ネイティブのアプリケーションから BDF を扱うための C のライブラリを作る。このメモは、なぜこの形にしたかの記録で、仕様そのものは bdf の `docs/spec.md` にある。

## 1. 目的

- Skia、cairo、QPainter、CoreGraphics のような描画 API を持つアプリケーション（Qt、GTK、.NET MAUI、Cocoa）から、BDF v1 をそのまま開いて描けること。
- 利用者がアップロードした文書を描く用途を含むので、不正な入力に対して参照実装と同じ上限を守り、メモリ安全であること。
- 既存の wire format と opset を変えない。libbdf は読み手であり、書き手ではない。

## 2. 層

```
core      コンテナ（single/split）、manifest（自前の JSON）、Part、deflate-raw（自前）、
          Object のデコード、WOFF2 → SFNT、テキスト run（選択・検索・リンク）、読み上げ用の構造、
          正規化つきの検索、暗号化の開錠、区間
raster    純粋な C のラスタライザ。bdf の raster/imagebdf の移植（§13）
adapters  core の命令列をフレームワークのキャンバスに流す薄い層（§16）
          skia/ (C++)  cairo/ (C)  qt/ (C++)  coregraphics/ (C)
```

core は形式だけを知り、描画を知らない。adapters は描画だけを知り、形式を知らない。raster は adapters の 1 つでもあるが、フレームワークに依存しない唯一の描き手なので、どの環境でも同じ絵を出す基準になる。

core のうち今あるのは読みの部分で、libc 以外に依存しない。JSON の読み手と inflate を自前で持つのは、依存を増やさないためと、単一ヘッダに収めるためである（§6）。例外は WOFF2 の Brotli で、google/brotli 1.1.0 のデコーダだけを `third_party/brotli` に vendoring した（MIT、無改変、出所と SHA-256 は同梱の README）。`BDF_WITH_BROTLI`（既定 ON）で入り、OFF のビルドは WOFF2 を `BDF_ERR_UNSUPPORTED` で断る。WOFF2 の復元そのものは Go の `font/woff2/decode.go` の移植で、glyf と loca の再構成（loca は長形式、`head.indexToLocFormat` を 1 に）、hmtx の再構成、タグ順の並べ替えと 4 バイト境界、チェックサムまで同じにしてあり、参照実装と同じバイト列を出す。Brotli の流れは、ディレクトリが言う大きさとその 1 バイト先までしか読まない（参照実装の `decompress` と同じで、短い流れと末尾の欠けた流れは拒否し、長い分は見ない）。

## 3. 参照実装との関係

- bdf の Go 実装が参照実装で、libbdf は検査される側である。`go/` の cgo ハーネスが同じバイト列を両方に通し、受理と拒否、manifest の構造、Part の復号したバイト列、資源表、命令列、エラーの位置と文言まで一致することを要求する。
- 入力は固定した版の bdf モジュールの testdata（`go/go.mod` の require）。全変換器の出力が揃っている。
- 依存は libbdf → bdf の一方向。bdf は libbdf を知らない。
- デコーダは Go の `decode.go`、`buf.go`、`path.go`、`paint.go`、`font.go`、`reader.go`、`manifest.go` を検査の順序まで含めて写した。Go の reader は最初の失敗を覚えて以後の読み取りを 0 にする。C の `bdfi_reader` も同じ振る舞いにしてあり、だから切り詰めた入力でも同じ位置・同じ文言で失敗する。
- manifest は encoding/json が参照実装の構造体を埋めるのと同じ規則で読む。知らないメンバーは無視、null は無いのと同じ、型の違うメンバーはエラー、重複したメンバーは最後が効く、整数のフィールドは整数リテラルだけ、float32 の範囲を超える数はエラー。合わせないと決めたのは、encoding/json がメンバー名を大文字小文字を無視して照合することと、base64 の中の改行を無視すること。どちらも仕様にない encoding/json の癖で、libbdf はそこだけ厳しい。差分 fuzz（`FuzzDoc`）は「libbdf が受理するものを参照実装が拒否しない」ことと「両方が開いた文書の Part が同じに読める」ことを要求し、逆向きは要求しない。
- テキストの抽出（`src/text.c`）は Go の `text.go` の移植で、歩き方、区切り（MARK と位置からの推定）、ALT_TEXT の扱い、上限（USE の深さ 64、再利用した Object から読む命令 2^27、run 2^22）、壊れた子 Object の扱い（そこまでの run を残して親の走査を続ける）まで同じにした。同じ上限を View の最上位 Object で数え続けること（`bdfi_use_limits`）も同じである。リンク（LINK の矩形の外接矩形と url）は Go の参照実装になく、TS の `text.ts` と `textlayer.ts` に合わせた。読み上げ用の構造（見出し・リスト・表・図）はまだ移していない。
- **位置の計算は積和を融合しない**。行列の積と点の変換は `a*b + c*d + e` の形で、コンパイラはこれを FMA（1 回だけ丸める積和）にしてよいことになっている。Go は arm64 で融合し、amd64 では融合しない。つまり参照実装自身がアーキテクチャで最後のビットが違う。libbdf は積を `volatile float` に置いてから足すことで、どのコンパイラ・どの CPU でも融合させない。位置が環境で変わらないことを優先し、参照実装とは amd64 でビット単位に一致する（bdf の fixture も amd64 を基準にしている）。差分テストは amd64 ではビット一致、arm64 では許容差つきで位置を比べ、位置から推定した区切りは「位置がビット一致なら一致」を要求する。Apple silicon では `GOARCH=amd64 CGO_ENABLED=1 go test` が Rosetta 経由で厳密な方を回す。
- Part 名の集合（どの子を歩いたか）は crit-bit 木で持つ。名前は文書が自由に選べるので、ハッシュ表だと衝突させて遅くできる。木なら 1 回 128 段までで済む。文書の Object のキャッシュは manifest の Part の番号で引く配列にして、表そのものを持たない。
- View のテキスト（`bdf_doc_view_text`）は `indexRuns`、検索用テキスト（`bdf_doc_search_text`）は `SearchText` の移植。シートのタイルのキーは参照実装が書く形（符号なし、先頭の 0 なしの `x,y`）だけを受け付ける。参照実装は `fmt.Sscanf` で読むので `01,0` のような形も通るが、その先で名前の引き直しに失敗するか同じタイルを 2 度読むかで、意味のある結果にならない。正規化つきの検索（NFKC、大文字小文字、かな）は Unicode の表が要るのでまだ入れていない。ホストの正規化（ICU、Foundation、Qt、.NET）で `bdf_doc_view_text` の結果を引けば足りる。
- inflate は参照実装（klauspost の flate）と受理が揃うようにした。不完全な Huffman 符号は長さ 1 の符号が 1 つだけの場合に限って受け付け、最後のブロックの後ろは読まない。`FuzzInflate` は両方向の一致を要求する。

## 4. C ABI の規則

`include/bdf/bdf.h` が ABI のすべてで、C++、Swift、C#（P/Invoke）、Go（cgo でも purego でも）、Python から束縛できるように次の規則を守る。

- ハンドルは不透明ポインタで、対になる `*_free` を持つ。
- 構造体を値で渡したり返したりしない。小さな POD（`bdf_path`、`bdf_paint`、`bdf_font`、`bdf_view`、`bdf_page`、`bdf_part_entry`、`bdf_header`、`bdf_error`）はポインタ経由で埋め、メモリを所有しない。
- 文字列は長さつきの UTF-8。便宜のため NUL も終端に置くが、中に NUL を含みうる。
- 大域状態を持たない。別スレッドの別文書は互いに触れない。
- 命令の読み取りは反復子（`bdf_instr`）と型つきのアクセサで行い、共用体を ABI に出さない。
- 入力はコールバック（`bdf_source`）で供給する。確保は実際のファイルの大きさに従い、manifest が言う大きさには従わない（参照実装と同じ）。コールバックは「大きさを尋ねる」と「埋める」の 2 段で、境界をまたいでメモリの所有を渡さない。
- `bdf_error.message` は静的文字列。参照実装が数値を埋め込む 3 つの文言（opset、flags、opcode）は数値なしにしてある。

## 5. テストの方針

- **単体テスト**（`tests/`、ctest）: 参照実装の `bdf_test.go` と `malformed_test.go` の事例を写したもの。切り詰め、未知の opcode、巨大な個数、不正な参照、manifest の数値の範囲、Part の範囲、inflate の上限。
- **サニタイザ**: CI は単体テストを ASan と UBSan 付きでもう 1 度回す。C ではこれが最も安い安全網で、既存の入力で起きるメモリ破壊の大半がここで出る。
- **差分テスト**（`go/`）: testdata の全文書、全 Part、全 Object、全フォントを Go と C の両方で読んで比べる。Linux では `go test -asan` で C 側も計装する。cgo が C ソースを直接コンパイルするので、ハーネスとライブラリは常に同じコミットになる。`go/` にあるのは `src/` と `third_party/brotli` の C ファイルへのシンボリックリンクで、`#include` で束ねたラッパーではない。Go のビルドキャッシュはパッケージ内のファイルの中身しか見ず、include 先の変更に気づかないので、ラッパー方式では C を直しても古いオブジェクトで `go test` が通ってしまう（実際に一度起きた）。リンクなら中身を読むのでキャッシュが追従する。
- **適合テスト**: bdf の `bdf conformance` が書く suite を `tests/conformance.c` が Go なしで流す（§7）。
- **fuzz は明示実行**: CI では回さない。探索は時間が青天井で CI に向かないという判断で、bdf の運用（パーサを変えたときに数分回す）と同じにした。探索は 2 系統ある。カバレッジ誘導とリーク検出は C の libFuzzer（`fuzz/`、object・inflate・manifest・doc・woff2・text・unlock・search・render の 9 本）、Go の参照実装との差分は `go test -fuzz`（`FuzzObject`、`FuzzInflate`、`FuzzDoc`、`FuzzWOFF2`、`FuzzText`、`FuzzIndexPart`、`FuzzUnlock`、`FuzzSealed`、`FuzzNFKC`、`FuzzGCM`、`FuzzP256`）。互いを何度も描く Object は「再利用した命令 2^27」の上限で止まるが、そこまで数秒かかる。fuzz のビルドは `BDF_MAX_REUSED_INSTRUCTIONS` を 65536 に下げ、単体テストは内部の `max_reused` を下げて、この経路を速く通す。見つかった入力は手で `fuzz/regress/<target>/`（ctest の `replay-<target>` が流す）か `go/testdata/fuzz/`（`go test` が流す）に入れて再生テストにする。`fuzz/corpus/` は fuzzer が育てる作業用のコーパスで、コミットしない。CI の `fuzz` ジョブは `workflow_dispatch` で分数を指定したときだけ動く。`go test -fuzz` は新しい経路に届いた入力を 1 件あたり最大 60 秒かけて最小化するので、文書まるごとを入力にする `FuzzUnlock` は実行数が伸びず止まって見える（0 execs/sec）。`-fuzzminimizetime 20x` を付けて回す。

cgo を選んで purego にしなかったのは、`go build -asan` が cgo にしか効かないことと、同じツリーの C ソースを静的に結合したかったからである。利用者向けに cgo なしの Go 束縛を出すなら、そのときは purego で別に作る。

## 6. 単一ヘッダとの両立

配布形態の 1 つとして、コア層を 1 本の `bdf.h` にできるようにしてある。開発は分割ソースのままで、`tools/amalgamate.py` が公開ヘッダ、内部ヘッダ、ソースをこの順に連結する。含めるだけなら宣言だけが見え、`BDF_IMPLEMENTATION` を定義した 1 つの翻訳単位にライブラリ全体が入る。そのための規則は次のとおり。

- 内部の識別子はすべて `bdfi_`（マクロは `BDFI_`）で始める。単一ヘッダでは含める側の翻訳単位に見えるので、衝突しない名前が要る。
- ファイルをまたいで共有する内部関数は `BDF_INTERNAL` を付ける。ライブラリのビルドでは空（隠し可視性）、単一ヘッダでは `static`。共有する内部の配列は持たず、関数で引く（`bdfi_dc_term`）。
- `BDF_STATIC` を定義すると `BDF_API` が `static` になり、公開関数も翻訳単位の外に出ない。
- 実装は C11。配列の指示初期化子（`bdfi_op_table`）と `void *` の暗黙変換を使っているので、C++ の翻訳単位には実装を入れない（宣言だけ含め、実装は 1 つの .c に置く）。
- CMake は Python があるとき `bdf_single_header` ターゲットで生成し、単体テストを単一ヘッダに対してもライブラリと同じ警告（`-Werror`）で回す。生成物は CI の成果物（`bdf-single-header`）にもなる。

第三者ライブラリ自体は単一ヘッダに入れない。WOFF2 の復元のコードは入っていて、Brotli は `BDF_HAVE_BROTLI` を定義して libbrotlidec（か `third_party/brotli`）を一緒にコンパイル・リンクすれば使え、定義しなければ `BDF_ERR_UNSUPPORTED` を返す。ラスタや画像コーデックも同じ扱いにする。

## 7. 適合テストの形式（bdf conformance）

bdf の `conformance` パッケージが、入力と「参照実装がそれをどう扱うか」の組を書き出す。期待値は参照実装を実際に走らせて記録したもので、各事例は「何を示すために書いたか」の判定（受理か拒否か）も持ち、生成時に両者が食い違えば生成が失敗する。だから suite が参照実装から離れることはない。

```
<dir>/suite.json
<dir>/inputs/<id>.bin
```

`suite.json` は `{"format": "bdf-conformance/1", "bdf": 1, "opset": 1, "generator": "...", "cases": [...]}`。事例は `id`、`kind`、`input`、`note`、`expect` を持つ。

| kind | expect |
|---|---|
| `single`（単一ファイルの文書） | `open`: `ok`/`error`。`ok` のとき `locked`、`views`（`{id, kind, pages}` の列）、`parts`（個数）、`reads`（`{h, read, size}`: 読むべき Part とその結果）、`allParts`（全 Part が読める） |
| `object`（Object Part） | `decode`: `ok`/`error`。`ok` のとき `walk`（全命令が読めるか）、`instructions`（終わりかエラーまでに読めた命令数） |
| `paths`（パス集の Part） | `decode`、`paths`（個数） |

`message` は参照実装のエラー文言で、人が読むためのもの。読み手が再現する必要はない。

事例は、ヘッダ（マジック、版、フラグ、予約バイト、manifest の範囲、deflate、暗号化フラグの整合）、manifest の数値の範囲、manifest の JSON（拒否するものと受け付けるもの）、Part の範囲と inflate の上限、書き手が作る文書、Object（切り詰めの全接頭辞、未知の opcode、巨大な個数、不正な参照）、パス集、そして testdata の全文書（受理）である。

libbdf 側は `tests/conformance.c` が suite を読んで同じ検査をする。suite は bdf の CI の成果物（`bdf-conformance`）とリリースの添付（`bdf-conformance-<tag>.tar.gz`）として配られる。libbdf の CI（`conformance` ジョブ）は添付を取りに行かず、`go/go.mod` が固定している版の bdf で同じスイートを書き出して回す。差分テストが突き合わせている参照実装と、適合テストの期待値を出した参照実装が、いつも同じ版になる。

## 8. 配り方

ソースは CMake ベースのこのリポジトリ 1 つで、配る先ごとに経路を変える。どれもリポジトリの中にあり、CI が経路ごとに利用側のプログラム（`packaging/consumer/main.c`）をビルドして確かめる。

| 相手 | 経路 | 置き場所 |
|---|---|---|
| C/C++ 一般 | 単一ヘッダ `bdf.h` | リリースのアセット。`bdf_single_header` ターゲット |
| CMake（Qt など） | `find_package(bdf)`、`bdf::bdf` と `bdf::<アダプタ>`、`FetchContent` | `cmake --install` |
| pkg-config（GTK） | `bdf.pc`、`bdf-cairo.pc`（プレフィックスは置かれた場所から相対で求めるので、インストール先を移せる） | `cmake --install` |
| Meson | `packaging/meson/bdf.wrap`（CMake のビルドをサブプロジェクトにする） | `subprojects/` にコピー |
| Conan 2 | ルートの `conanfile.py` | `conan create .` |
| vcpkg | `packaging/vcpkg/bdf`（オーバーレイ ポート） | `--overlay-ports` |
| Swift、Xcode | ルートの `Package.swift`: C のソースをそのままビルドする `CBDF`、Core Graphics アダプタの `CBDFCoreGraphics`、その上の薄い Swift の層 `BDF` | リポジトリをパッケージ依存に足す |
| Xcode（バイナリ） | `bdf.xcframework`（macOS、iOS、iOS シミュレータ） | `packaging/xcframework.sh`、リリースのアセット |
| .NET（MAUI、SkiaSharp） | NuGet パッケージ `LibBdf`（P/Invoke と `runtimes/<rid>/native/` の共有ライブラリ）、`LibBdf.SkiaSharp`（`SKCanvas` に描くアダプタ） | `dotnet/`、リリースのワークフローが pack する |

**当初の計画から変えたところ**。Swift は別リポジトリ `swift-bdf` に xcframework の binaryTarget を置く計画だったが、このリポジトリの `Package.swift` がソースからビルドする形にした。C のソースだけで依存がないので SwiftPM がそのまま扱え、リポジトリもホストするバイナリも増えない。xcframework とそのチェックサムはリリースのアセットに入るので、binaryTarget が要るようになったらそこから作れる。

**.NET のアダプタは C# で書いた**。SkiaSharp の上では、C++ の Skia アダプタ（`adapters/skia`）をネイティブに同梱するより、コアのプレイヤー（§16）のコールバックを C# の関数ポインタ（`UnmanagedCallersOnly`）で受けて `SKCanvas` を呼ぶほうが、SkiaSharp が持つ Skia のバイナリとバージョンを合わせる問題が起きない。例外は C のコアをまたがせない（C++ のアダプタと同じ）。

**リリース**。`v<バージョン>` のタグで `.github/workflows/release.yml` が動き、単一ヘッダ、3 つの OS のバイナリ（静的と共有、CMake パッケージと pkg-config 込みのインストール ツリー）、xcframework、NuGet パッケージを作って、下書きのリリースに付ける。タグとヘッダのバージョンが違えば止まる。付ける前に `packaging/release-files.sh` が、全部のファイルが揃っていること、ヘッダのバージョンのものであること、中身（NuGet パッケージなら 4 つのプラットフォームの共有ライブラリ）を確かめる。タグなしでも、手で起動したときと、このワークフローやそのスクリプトを変える PR では同じビルドと検査をしてリリースだけを作らないので、タグを打つ前に予行が済んでいる。レジストリ（vcpkg、ConanCenter、WrapDB、nuget.org）への公開はしていない。リリースのあと手で直すのは、vcpkg のポートの `SHA512` と Meson の wrap の `revision` の 2 か所。

ABI は SONAME（`libbdf.so.0`）と `bdf_version()` を持ち、コンパイラが違っても壊れないことを CI の MSVC と clang の両方のビルドで確かめる。依存は vendoring した Brotli のデコーダだけで、画像のデコーダもフォントの読み手も自前（§14、§15）なので、既定のビルドはどの経路でも自己完結している。

## 11. 暗号化と区間

**部品は自前で持つ**。当初は Mbed TLS か platform の API（CommonCrypto、CNG、OpenSSL）を vtable で差し替える案だったが、やめた。読み手に要るのは開錠だけで、SHA-256、HMAC、PBKDF2、HKDF、AES-256、AES-KW のアンラップ、GCM の復号、P-256 の ECDH の 8 つに限られる。乱数も署名も要らない（ECDH の秘密鍵は呼び出し側が OS の乱数で作って渡す。`bdf_p256_public_key` はその公開鍵を返すだけ）。`src/crypto.c` は 900 行あまりで libc にしか依存せず、単一ヘッダにそのまま入る。外部ライブラリを 1 つ足すと、単一ヘッダ、vcpkg、NuGet、xcframework のすべてで「暗号ライブラリをどう持ち込むか」が利用者の問題になる。その代価に見合わないと判断した。

**検証**。部品ごとに Go の標準ライブラリと突き合わせている（`go/crypto_test.go`: ランダムな入力での一致と、`FuzzGCM`、`FuzzP256`）。C だけのテストは、Go が計算した既知解（RFC 4231、6070、5869、3394、FIPS 197 の入力を含む）を `tests/crypto_vectors.h` に持つ。文書の単位では、testdata の全文書を参照実装で暗号化して両方の読み手で開け、manifest と全 Part を比べる。改竄は 1 バイトずつ変えて、開くものと拒否するものが一致することを確かめる。

**サイドチャネルへの立場**。

- P-256 のスカラー倍は秘密鍵に依存しない。完全な加法公式（Renes–Costello–Batina、a = −3。Go の `nistec` と同じ）を使い、常に倍算と加算の両方を計算して、結果を定数時間の選択で取る。体の演算は 32 ビット limb の Montgomery 乗算で、分岐は最後の減算の選択だけ（これもマスク）。
- GCM のタグ、AES-KW の検査値の比較は定数時間。タグが合わなければ平文は 1 バイトも書かない。
- AES は S-box の表引き、GHASH は 4 ビットの表引きで、**キャッシュ タイミングには耐性がない**。Go の `crypto/aes` も AES-NI のない環境では同じ表引きに落ちる。読み手は自分の文書を自分の鍵で開けるだけなので、攻撃者が同じ機械で時間を測りながら復号を何度も走らせる場面は想定しにくい、という判断である。共有ホストで他人の文書を復号するサーバーに使うなら、この前提は成り立たない。
- 鍵と、鍵から作った表は、使い終わったら `bdfi_wipe`（volatile 経由の書き込み）で消す。パスワードの NFKC 形もそうする。

**パスワードの NFKC**。spec はパスワードを NFKC にして UTF-8 にすると定める（bdf 0.1.6 までは NFC だった。PDF 2.0 の SASLprep や NIST SP 800-63B と同じ向きで、全角と半角、半角カタカナと全角カタカナが同じパスワードになる。大文字小文字とかなの種類は区別する）。NFC で試し直すことはしないので、古い版が「NFKC で変わる文字を含むパスワード」で封印した文書は開かない。これは参照実装と同じ。libbdf の正規化は NFKC の 1 本だけになり、パスワード、フォントの家族名、検索が同じ関数（`bdfi_nfkc`、`bdfi_nfkc_points`）を使う。`src/unicode_nfc.h` は `golang.org/x/text` の表から `go/genunicode` が作る（Unicode 17.0.0、分解 2,081 件、結合クラス 403 区間、合成 961 対、表は約 55 KB）。ハングルは算術。`FuzzNFKC`（以前の `FuzzNFC`）で x/text と突き合わせて、2 つ食い違いが出た。

- x/text は結合文字が 30 個を超えて続くと U+034F（CGJ）を挟む（Stream-Safe Text Format）。これは正規化そのものではなく、ブラウザの `String.prototype.normalize` は挟まない。libbdf は挟まない。つまり **結合文字を 31 個以上続けたパスワード** は、Go の書き手と TS の読み手の間で鍵が食い違う（bdf 側の課題）。libbdf は TS と同じ鍵になる。差分テストはこの入力を飛ばす。
- 不正な UTF-8 のうち、末尾で足りないマルチバイトの先頭バイトは、x/text が残りをそのまま写す。libbdf はこれに合わせた（パスワードが正しい UTF-8 なら関係しない）。

**上限**。`iter` は 1〜10,000,000、password スロットの合計も 10,000,000 まで、ecdh スロットは 16 個まで。参照実装と同じ値で、同じ順に検査する。遅い CPU 向けに `BDF_MAX_KDF_ITERATIONS` をビルド時に下げられる（fuzz のビルドは 2,048）。

**開錠後の文書**。`bdf_doc_unlock` が成功すると、封印された manifest が文書の manifest になり、`bdf_doc_view` などはそれを返す。外側の manifest は Part を取りに行くためだけに残る。封印された manifest の `parts[]` が指す `sealed` が外側に無ければ開錠の時点で拒否する（参照実装は Part を読むときに気づくが、結果は同じ）。開錠は文書を書き換えるので、スレッド間で共有する前に済ませる。

**区間（§3.6）**。区間の文書は形としては 1 つの文書で、全ページの枠を持ち、自分のページにだけレイヤがある。`bdf_doc_add_segment(doc, segment)` は、segment のページを doc の同じ位置に入れ、segment の Part を doc の検索対象に足す。先に来た区間が持つ Part（共有のフォントやマスター）は後の区間に入っていないので、Part は「自分、次に足された区間の順」で探す。所有権は doc に移り、`bdf_doc_free(doc)` がまとめて解放する。渡した文書をさらに別の文書へ足すこと、渡した文書に区間を足すことは `BDF_ERR_ARG` で断る（Part の通し番号がずれるのと、二重解放を防ぐため）。view の id とページ数が違う文書は「別の文書の区間」として拒否する。区間ごとに鍵が違ってよく、平文の文書に区間を足すこともできる。

## 12. テキストの構造と検索（TS 実装が参照）

読み上げ用の構造（§7.8 の「構造」）と正規化つきの検索は、bdf の Go 実装には無く、TypeScript のリーダー（`packages/core/src/text.ts` の `extractContent`、`search.ts` の `TextSearch`）だけが持つ。Go との差分テストが組めないので、**TS 実装を node で走らせて正解にする**。

- `tools/structure-oracle.mjs` と `tools/search-oracle.mjs` が、ピン留めした bdf モジュールの testdata を TS 実装で読み、結果を `go/testdata/structure.txt.gz`（328 Object、4,157 ノード、図 178 個）と `search.txt.gz`（索引 168 本、2,594 クエリ、4,792 ヒット）に書く。`go test` はこれと libbdf を行単位で比べる。node も TS も要らないので CI で回る。
- testdata は書き手が作る素直な入力しか持たない。`LIBBDF_BDF_CHECKOUT` に packages/core をビルド済みの bdf のチェックアウトを指定すると、`TestStructureRandom` と `TestSearchRandom` が乱数で作った Object と索引を両方に通して比べる（既定で 2 万件と 1 万件。手元では構造 30 万 Object・約 170 万ノード、検索 30 万索引・約 166 万ヒットまで一致を確認）。fuzz と同じく明示実行。
- 検索の正規化は 2 段。文字列の NFKC は libbdf の表（`unicode.c`。Go の x/text から書き出した Unicode 17.0）で行い、その後の 1 文字ごとの畳み込み（小文字化・カタカナ→ひらがな・U+2212→`-`）は表 `src/unicode_fold.h`（約 6 KB）を引く。この表は、NFKC で変わらない全コードポイントについて TS の `normalizeQuery` に聞いた結果そのもの（`tools/gen-search-tables.mjs`）。Unicode の版は生成に使った node のもの（17.0）で、libbdf の NFKC の表と同じ版でなければならない。
- 正規化が TS と同じであることは 2 つのテストで見る。`TestSearchNormalizeMatchesXText` は全コードポイントと乱数の文字列 20 万本を x/text の NFKC と比べる（CI で回る）。`TestSearchNormalizeAll` は `LIBBDF_BDF_CHECKOUT` を指定したときに、全コードポイントを単独で、また合成しうる相手（結合文字、濁点、ハングルの字母、分解した形）と並べて、1,731,889 本を TS の `normalizeQuery` と比べる。`TestSearchEveryCharacter` は同じく明示実行で、全コードポイントを「ASCII の字の後」「終声を取れるハングルの音節の後」「自分自身の後」に置いた索引 139,008 本を両方で検索し、断片の切れ目（ヒットの範囲に出る）まで比べる（約 445 万ヒットが一致）。

**構造**。ノードは開いた順の配列で、各ノードが親の番号を持つ。run とリンクは属するノードの番号を持つ。MARK の扱いは TS と同じ（葉の MARK は次の run の段落の種類を予約、構造の MARK はその場で効く、LIST の直下の run は暗黙の項目、TABLE の直下の run は caption、開いていない END は何もしない）。見出しのレベルは JavaScript の `Number()` が 1〜6 の整数と読むもの（`" 3 "`、`"3.0"`、`"0x3"`、`"30e-1"` も 3）。丸めて初めて整数になる 10 進数（`5.9999999999999999999999`）だけは TS と違ってレベルなしになる。

**図の範囲はビット単位で TS と同じ**。TS は変換行列を倍精度で持ち、Go（と libbdf の run の位置）は単精度で持つ。図の範囲のためだけに倍精度の行列を並べて持ち、積和は `bdfi_muld`（volatile 経由）で FMA を禁じ、`Math.min` / `Math.max` の NaN と −0 の扱いも写した。結果は float に丸めて返す。ALT_TEXT を子 Object が描く場合の x は、TS が倍精度の和、Go が単精度の和で、図の範囲には前者を使う（乱数テストが見つけた 1 ulp の差）。図の中のテキストの幅は、字送りが無ければ「サイズ × UTF-16 の単位数 × 0.5」で、UTF-16 の長さはブラウザのデコーダと同じ数え方（不正なバイト列は最大部分列ごとに U+FFFD 1 つ。先頭の BOM は文字列を読むときに落ちている）。

**検索**。正規化は**文字列単位の NFKC**。文字ごとではないので、結合文字で書いた「e + ◌́」と合成済みの「é」、半角の「ｶﾞ」と「が」、ハングルの字母の並びと音節は、文書とクエリのどちらがどう書いていても互いに見つかる。アクセントの無い「e」は「é」に当たらない（合成済みで書かれているときと同じ）。クエリは全体を NFKC にしてから 1 文字ずつ畳む。run は run ごとに正規化する（前の run の末尾の字と次の run の先頭の結合文字は合成しない。TS と同じ）。

ヒットを元のテキストに戻すために、run のテキストを「単独で正規化できる最小の断片」に切る（TS の `pieces` の移植）。文字は 1 つで 1 断片。ただし、その文字の NFKC が結合文字（General Category M）で始まるか、断片に足した結果が「断片の NFKC + その文字の NFKC」と違うときは、前の断片に入る（アクセント、濁点、ハングルの中声と終声）。ASCII は常に新しい断片を始める。断片は 32 文字まで（TS の `MAX_PIECE`）。結合文字を何万個も並べたテキストで、足すたびに断片全体を正規化し直して 2 乗の時間がかかるのを防ぐためで、33 文字目からは別の断片になる。正規化後の各文字は「元の run と、断片の始まりと終わりのバイト位置」を持つ（1 文字あたり 16 バイト）ので、ヒットは断片の単位で返る。「é」で探すと「e + ◌́」の 3 バイト全部が範囲になる。

TS は 1 文字ごとに `normalize` を 2 回呼ぶ。libbdf は、分解を持たず、結合クラスが 0 で、結合文字でもない字（漢字、濁点の無いかな、ほとんどの字）については正規化を呼ばない。そういう字は NFKC で変わらず、前のテキストを変えるのは前の断片の最後の字と合成するときだけなので、合成の表を 1 回引けば TS の比較と同じ答えが出る（ハングルの中声と終声、2 つの部分からなる母音記号がこれに当たり、そのときだけ正規化する）。日本語のテキストで 13 MB/s が 38 MB/s になった（リリース ビルド、Apple M 系）。

ヒットの位置は run のテキストの**バイト**オフセットで返す（TS は UTF-16 の単位）。前後の文脈は文字数で数える（TS は UTF-16 の単位なので、BMP 外の文字を含む文脈だけ長さが違う）。正規化後の長さは 2^26 文字で打ち切る（1 文字が最大 18 文字に展開されるため）。

**上限**。ノードは 2^22 個まで（run、リンクと同じ）。開いた図は描画命令のたびに全部を広げるので、広げるのは内側 64 段までとし、それより深い図は大きさ 0 のままにする（TS に上限は無いが、数万段の入れ子と数百万の描画命令で二乗の時間がかかる）。

**参照実装どうしの食い違い**（libbdf は Go に合わせた。どちらも書き手が作らない入力）:

- SAVE / RESTORE がマスク（MASK_BEGIN〜MASK_END）の境界をまたぐ命令列。Go の `text.go` はマスクの中を丸ごと飛ばし、TS の `text.ts` はマスクの中の RESTORE も実行して MASK_END でもう 1 度戻す。マスクの後の run の位置が変わる。

**直った食い違い**。文字列の先頭の BOM は、TS が `TextDecoder` で落とし、Go は残していた。bdf 0.1.6 の後で仕様（§6）が「先頭の U+FEFF 1 つは文字列に含めない。書き手も書かない」と決まり、Go も読むときに落とすようになった。libbdf も文字列を読む 1 か所（`bdfi_rd_string`）で落とすので、Object の文字列、索引の run、検索、図の幅のどれにも BOM は現れない。

## 13. ラスタライザ

`raster/imagebdf`（Go）を演算の順序と型まで同じにして C に移した。**参照実装と 1 バイトも違わない絵を出す**ことを目標にし、ベクタの中核ではそれを達成している。libc 以外に依存せず、core と同じライブラリ・同じ単一ヘッダに入る。

**構成**（`src/r*.c`、`render.c`、内部ヘッダは `raster_internal.h`）:

| ファイル | Go の対応 | 内容 |
|---|---|---|
| `rmath.c` | `math` パッケージ | sin、cos、tan、atan、atan2、asin、acos、hypot、max、min |
| `rpath.c` | `path.go` | 変換行列、Path2D（ellipse、arcTo、roundRect）、折れ線化 |
| `rscan.c` | `scan.go` | マスク、矩形の厳密な被覆、スキャンライン（1 行 16 サンプル、x は厳密） |
| `rstroke.c` | `stroke.go` | 線の輪郭（継ぎ目、端、破線）、輪郭点と破線数の上限 |
| `rsurface.c` | `surface.go` | float の乗算済み RGBA キャンバス、合成演算 26 種とブレンド モード |
| `rpaint.c` | `paint.go` | グラデーションの 1024 段の表、線形・放射（2 円）・円錐 |
| `rdraw.c` | `draw.go` | 状態、命令の実行、クリップ、グループ、ソフト マスク、影 |
| `render.c` | `imagebdf.go`、`object.go` | ページ、連続ビュー、シートと罫線、単体の Object、公開 API |

**同じ絵にするために必要だったこと**。

- **FMA を使わない**。積と和を 1 命令にまとめると丸めが 1 回になり、100 万画素に 1 つが 1 段ずれる。Go は amd64 でまとめず、arm64 でまとめる。libbdf はどこでもまとめない（`raster_internal.h` が各コンパイラの pragma で切り、CMake も `-ffp-contract=off` を付ける）。gcc 12（aarch64、`-std=gnu11 -O2`）で確かめた: pragma を外すとスキャンラインに FMA が 199 個入り、テストの絵が 2 枚変わる。付ければ 0 個で、絵は同じ。
- **Go の math を移植する**。libc の sin や atan は実装ごとに最後の 1 ビットが違い、Go とも違う。Go の実装（Cephes 由来、BSD ライセンス。表記は `third_party/go-math/LICENSE`）を `rmath.c` に移した。sqrt、fmod、floor、ceil、round は厳密な演算なので libm のものを使う。amd64 で Go と約 480 万の入力がビット単位で一致。
- **定数を Go と同じに丸める**。Go の定数式は使うまで任意精度なので、`3*math.Pi/2` は 3π/2 に最も近い double で、π の double の 3 倍ではない。必要な定数は Go に計算させて 17 桁で書いた。
- **整数への変換を amd64 に合わせる**。NaN や範囲外の値を int にすると Go は処理系依存で、amd64 では最小の int になる。C では未定義なので、その値を明示的に返す（`segmentsFor`、円の分割数、ソフト マスクの輝度）。
- **`math.Max` と組み込みの `max` を区別する**。前者は ±Inf が NaN に勝ち、後者は NaN が勝つ。

**検証**。Go 側のハーネスが、乱数で作った描画（全命令をでたらめな順に: パス、塗りと線、破線、クリップ、グラデーション、合成演算、影、グループ、マスク、USE）と文書（Object どうしの USE、複数レイヤーのページ、本文で切った帯、タイルと罫線のシート）を両方で描いて画素を比べる。amd64 では完全一致を要求する。手元で確認した範囲は、単体の Object 約 2 万 4 千個（約 14 億画素）、文書約 2,000 本・3 万枚（約 7.5 億画素）、testdata のうち図形だけでできたページ 36 枚（PDF 由来のページは文字をアウトラインで描くので対象になる）。arm64 では Go の側が FMA で別の絵を出すので、近いことだけを見る。

C だけのテスト（`tests/test_render.c`）は、手で画素を言える描画と、**参照実装（amd64）が描いた絵のハッシュ**（`tests/render_vectors.h`、`GOARCH=amd64 go run -C go ./genvectors tests render`）を持つ。後者は「どのプラットフォームのどのコンパイラでも同じ絵」の検査で、clang（arm64、Debug と Release）と gcc 12（aarch64、`-O0`〜`-O3`）で通っている。CI の MSVC と x86 もこれで確かめる。

**参照実装と違えたところ**。

- グループやマスクのキャンバスは参照カウントで持つ。Go は GC とキャンバスの再利用プールに任せているので、壊れた命令列（マスクの中で始めたグループを残したままマスクを終える）では、終わったマスクのキャンバスに描き続け、そのキャンバスが別のグループに貸し出されることがある。libbdf では終わったキャンバスへの描画はどこにも出ない。well-formed な命令列では同じ絵になる。
- キャンバスの再利用プール（`Renderer.free`）と、絵を変えない近道を使わない描き方（`plain`）は持たない。前者は速度だけの話で、必要になったら足す。
- 警告の文面は英語で、Go とほぼ同じだが一字一句は合わせていない。

**上限**は Go と同じ値: 画像 64M 画素、パスの点 2^20、スキャンの仕事量 2^24、線の輪郭点と破線 2^20、グループとマスク 64 段、状態 1024、開いているキャンバスとクリップのメモリ（画像 8 枚分か 64 MiB）、描き直す命令 2^24、影のぼかし 1024 px。最後の 2 つは `BDF_MAX_REUSED_DRAWN`、`BDF_MAX_SHADOW_BLUR` でビルド時に下げられる（fuzz のビルドは 65536 と 16）。ぼかし 1024 px の影は 1 回の描画で 1,000 万要素を 3 回なめるので、影つきの描画を数万個並べた文書は参照実装でも libbdf でも時間がかかる。これは bdf 側の課題として残る。

**まだ描かないもの**（この節を書いた時点。画像は §14）。テキスト（`FILL_TEXT`、`STROKE_TEXT`）、SVG 画像、`FILTER`。出会うと警告を 1 度出して飛ばす。

## 14. 画像

`IMAGE`、`IMAGE_SUB`、パターンの塗りを描く。画像パートのビットマップ（PNG、JPEG、GIF、BMP、WebP）は libbdf が自分でデコードする。libpng や libjpeg は使わない。

**なぜ自前か**。ラスタライザの目標は参照実装と同じ画素で、参照実装は Go の `image/png`、`image/jpeg`、`image/gif`、`golang.org/x/image` の `bmp`、`webp` でデコードする。JPEG と非可逆 WebP は実装ごとに逆 DCT と色変換の丸めが違い、壊れたファイルをどこまで受け付けるかも違うので、別のデコーダでは「同じ絵」にならない。そこで **Go のデコーダを演算の順序まで同じにして移植した**（BSD ライセンス。表記は `third_party/go-image/LICENSE`）。外部依存が増えないので、単一ヘッダにもそのまま入る。

| ファイル | Go の対応 | 内容 |
|---|---|---|
| `img_png.c` | `image/png` | 全色型・全ビット深度、Adam7、tRNS。IDAT は Go の `bufio` と同じ区切りで読む（後述） |
| `img_jpeg.c` | `image/jpeg` | ベースラインとプログレッシブ、グレー・YCbCr（各サブサンプリング）・RGB・CMYK/YCCK |
| `img_gif.c` | `image/gif`、`compress/lzw` | 最初のフレームだけ（`gif.Decode` と同じ） |
| `img_bmp.c` | `x/image/bmp` | 1・2・4・8・24・32 ビット、V4/V5 ヘッダ |
| `img_webp.c`、`img_vp8.c`、`img_vp8l.c` | `x/image/webp`、`vp8`、`vp8l`、`riff` | 非可逆、可逆、非可逆＋アルファ |
| `rimage.c` | `image.go`、`imgconv` の `Sniff`・`Orientation`・`Orient`、`paint.go` | 形式の判定、EXIF の向き、縮小コピー（ミップ）、サンプリング、画像とパターンのシェーダ |

各デコーダは 2 つの関数で、インターフェースは `src/image_internal.h` にある。`bdfi_<fmt>_decode` は、`imgconv.Decode`（`DecodeConfig` で大きさを確かめてから `Decode`、どちらかの panic もエラー）と、その結果を `draw.Draw(..., draw.Src)` で `*image.RGBA` にする変換までを 1 つにしたもので、乗算済み RGBA 8 ビットを返す。変換は Go が返す画像の型（`NRGBA`、`YCbCr`、`NYCbCrA`、`Gray`、`Paletted`、`CMYK` …）ごとに通る道が違うので、型ごとにその整数演算を再現している。

**「同じ」の定義**。(1) 参照実装がデコードできる画像は、同じバイト列になる。(2) 参照実装が拒否する入力は拒否し、受け付ける入力は受け付ける。Go のデコーダが壊れたファイルで panic する箇所（添字の範囲外など。参照実装は recover してエラーにする）は、C では明示的な検査にした。

(2) のために PNG で必要だったのが **`bufio` の先読みの再現**。Go の `image/png` は IDAT を `zlib` → `bufio.Reader`（4096 バイト）越しに読み、圧縮ストリームが終わった時点で「今の IDAT チャンクに未読のバイトが残っていたらエラー」とする。残っているかどうかは `bufio` がどこまで先読みしたかで決まるので、ストリームの後ろにゴミがある PNG は、ゴミの位置と長さ次第で通ったり通らなかったりする。libbdf の inflate は入力を「区間」単位で受け取れるようにしてあり（`bdfi_pull`）、PNG は Go と同じ大きさの区間（バッファが空のときに 4096 バイトか、無圧縮ブロックの大きな読み出しならその長さ）を IDAT チャンクから渡す。これで受理・拒否が一致する。

**サンプリング**は `image.go` のとおり。縮小コピーは 2×2 の箱で作り、必要になったときに作る。画像の描画は、なめらか（`SMOOTHING` が有効、または縮小コピーを使うとき）なら 4 点の線形補間、そうでなければ最近傍。パターンは常に線形補間で、繰り返す方向は端で回り込む。`math.Log2` も移植した（`rmath.c`）。

**メモリ**。デコードする画像は 1 枚 1 億 480 万画素まで（`imgconv.MaxDecodePixels`。`BDF_MAX_DECODE_PIXELS` で下げられる）。レンダラがデコード済みで持つ画像は合計 2 億 6,800 万画素までで、超えるときは「今描いている絵が使っていない画像」を古い順に手放す（`makeRoom`）。スタイルが指している画像は必ず今の絵が使ったものなので、手放した画像を指すポインタは残らない。

**JPEG のスキャンの数**。JPEG のデコーダはスキャン 1 つごとに画像の全ブロックを 1 周するので、スキャンだけを並べた小さなファイルが桁違いの時間を食う（65 KB、8192 × 8192 画素、スキャン 500 個で 12 秒。移植したデコーダも同じ形をしている）。libbdf のファザーが遅い入力として見つけ、bdf 0.1.6 の後で参照実装が上限を持った: **JPEG は最初の 100 個のスキャンまで読む**（`imgconv.MaxJPEGScans`）。断るのではなく、その後ろを切って画像の終わりを付け、そこまでのスキャンが描く絵にする。libbdf は同じ規則でスキャンを数え（`bdfi_jpeg_scans_end`。デコーダがセグメントの間でマーカーを探すのと同じ読み方で、EXIF のサムネイルのようなセグメントの中のスキャンは数えない）、同じバイトで切り、同じ言葉で警告する。`BDF_MAX_JPEG_SCANS` で下げられるが、下げると参照実装と同じ絵ではなくなる。

**検証**。デコーダは 1 つずつ、Go のデコーダと差分テストした（`go/<fmt>_test.go`、共通部は `go/imagediff_test.go`）: testdata の画像パート、Go と x/image の testdata、テストが作る画像、合成画像から外部のエンコーダで作った小さなファイル（`go/testdata/images/`）、それらを壊したもの、Go のファザー（Go 側のカバレッジで誘導されるので、Go が独自の道に入る入力を見つける）。描画は、画像を含む乱数の文書（全体・一部・パターン・なめらかさの切り替え・EXIF の向き・デコードできない画像）を両方で描いて画素を比べる。数字は PR に書いた。

**まだ描かないもの**。AVIF（参照実装も描かない）。SVG 画像は §17。テキストは §15。

## 15. テキスト

`FILL_TEXT` と `STROKE_TEXT` を描く。FreeType も HarfBuzz も使わない。参照実装がそれらを使わず、自前の `internal/sfnt` と `internal/fontdb` でグリフの輪郭を取り出して自分のラスタライザで塗っているので、それを移植すれば同じ絵になる。

| ファイル | Go の対応 | 内容 |
|---|---|---|
| `sfnt.c` | `internal/sfnt`（`sfnt.go`、`outline.go`、`bounds.go` の CFF） | 表の一覧、cmap（形式 0・4・6・12）、送り幅、TrueType の輪郭（合成グリフ、暗黙の点）、CFF の Type 2 チャーストリング（サブルーチン、flex） |
| `fontdb.c` | `internal/fontdb`（`fontdb.go`、`resolve.go`）、`sfnt/coverage.go` | フォントの集合、name 表からの家族名、太さと傾きの照合、代わりの家族、総称、フォールバックの並び、cmap だけでの「この字を持つか」 |
| `rtext.c` | `text.go` | FONT 命令ごとの面の並び（チェーン）、字の配置、表示順、ベースライン、合成ボールドの太さ |
| `rdraw.c`（text、strokeText） | `draw.go` | 配置したグリフの塗りと線、合成ボールド（輪郭を丸い継ぎ目の線でなぞって足す）、合成イタリック（0.25 の傾き） |
| `unicode.c`、`unicode_text.h` | `x/text` の `norm`・`bidi`、`unicode.ToLower` | 家族名の比較用の正規化（NFKC、小文字、空白とハイフンを除く）、字の方向 |

**レイアウトは参照実装のもの**で、ブラウザのものではない。1 字 1 グリフで、合字もカーニングもなく、アラビア文字の字形選択もミラーリングもない。右から左の並びは「方向が同じ字の並びを反転し、段落が右から左なら並びの順も反転する」だけの簡略版（`visualOrder`）。`FILL_TEXT` の送り幅（advance）が付いていれば、手元のフォントでの幅との差が 0.5% を超えるときに横に伸縮して合わせるので、作成時と違うフォントで描いても行の幅は合う。これがプレビュー用として十分というのが参照実装の判断で、libbdf はそれに従う。ブラウザと同じ字形が要る用途は、ネイティブのテキスト API を使うアダプタの仕事になる。

**フォントの出どころは 2 つ**。

1. 文書が持つフォント パート（TrueType、OpenType/CFF、WOFF2）。太さと傾きはフォントに登録されていない扱いなので、FONT 命令が太字や斜体を言えば合成する。
2. 名前で指すフォント（HTML、Markdown、EPUB 由来の文書と、埋め込みフォントに無い字）。参照実装はシステムのフォント ディレクトリを走査するが、**libbdf は走査しない**。アプリケーションが `bdf_fonts` にフォント ファイルを足して（`bdf_fonts_add` はメモリ上のファイル、`bdf_fonts_add_file` はパス）、`bdf_render_options.fonts` で渡す。ディレクトリの走査は OS ごとの API が要り、単一ヘッダの C11 に収まらないのと、どのフォントを使うかはアプリケーションが決めることだからである。渡さなければ、名前で指すテキストは警告を出して描かない。

集合の中での探し方は参照実装と同じ: 家族名そのもの → 見た目や字幅が合う代わりの家族（Arial に Liberation Sans、メイリオに Noto Sans CJK JP など、`resolve.go` の表）→ 同じ種類の総称（sans-serif、serif、monospace）→ アルファベット順で最初の家族。字が無いときのフォールバックは、総称の欧文、CJK の並び、記号フォント、そして集合が 64 面以下なら残り全部。参照実装に同じファイルを同じ順で `FontDirs` として渡し `NoSystemFonts` を立てれば、両者は同じ面を選ぶ。テストはこの形で比べる。

`bdf_fonts` は作ったあと変更しない読み取り専用の集合で、複数スレッドのレンダラが共有できる。レンダラが読んだ面（グリフの輪郭のキャッシュを含む）と cmap はレンダラごとに持つ。パスで足したファイルは、名前だけを足すときに読み、グリフはその面で最初に描くときに読む。パスはどの OS でも UTF-8 で、Windows では UTF-16 に直して開く（C ライブラリの `fopen` はシステムのコード ページでパスを取るので、日本語の名前のフォントが開けないことがある）。UTF-8 でないパスと、UTF-8 として開けなかったパスは、そのあと C ライブラリの流儀でも試す。

**同じ絵のために気をつけたところ**。

- cmap は Go が map に書き込む順をなぞって「同じ字への最後の書き込みが勝つ」ようにした（区間が重なる壊れた cmap でも同じ字形を選ぶ）。全部分表の合計が 440 万字を超えるフォントは Go と同じく読まない。
- 「この字を持つか」（`HasRune`）は、Go と同じく、面をまだ読んでいなければ cmap 表だけを見る厳しい読み手（整列していない部分表は使わない）、読んでいれば実際の cmap で答える。
- 合成ボールドの太さの式の定数（1/24 と 1/32 − 1/24）は、Go の定数式の丸めに合わせて書いた。
- 家族名の正規化は NFKC のあと小文字化（Go の `unicode.ToLower`。合成してから小文字にする順序も同じ）。表は `go run -C go ./genunicode src/unicode_nfc.h src/unicode_text.h` で x/text と Go から作る。

**参照実装と違えたところ**。CFF の INDEX の最後のオフセットが表の終わりで切れているフォントで、Go は範囲外を読んで panic し、その絵全体が失敗する。libbdf はそのフォントを「輪郭なし」として扱い、ページの残りは描く。差分ファザー（`FuzzFont`）は、参照実装がページを諦めた入力だけを比較から外している。

**検証**。testdata の文書の全ページ（テキストは埋め込みフォントと bdf のテスト用フォントで描く。SVG 画像を使うページは §17 で加わった）が amd64 でバイト単位に一致。乱数の文書（塗りと線、埋め込みと名前、壊したフォント、WOFF2、両方向、揃え、送り幅への合わせ込み）も同様。テスト用に作るフォント（`go/fontbuild.go`: 直線と 2 次曲線と合成グリフの TrueType、3 次曲線とサブルーチンの CFF）は誰の著作物でもないので、参照実装の描いた絵のハッシュと一緒に `tests/render_vectors.h` に入れて、C だけのテストでもテキストを確かめている。

## 16. キャンバスとアダプタ

アダプタは「core の命令列をフレームワークのキャンバスに流す薄い層」（§2）だが、命令列をそのまま渡すと薄くならない。SAVE と RESTORE がグループやマスクをまたぐときの扱い、USE の再帰と上限、パターンと画像のデコード、フォントの選択とテキストの配置、ソフトマスクは、どれも形式の知識で、アダプタごとに書けば 4 回書くことになり、4 通りに間違える。そこで core に**プレイヤー**（`src/rcanvas.c`）を置いた。プレイヤーは命令列をラスタライザ（`rdraw.c`）と同じ順序と上限で実行し、描くところだけを `bdf_canvas` の関数表に渡す。アダプタはその表を埋めるだけで、cairo が 450 行、Core Graphics が 500 行ほどになる。

```
bdf_play_page(renderer, view, page, scale, &canvas, &err)   ページ、スクロール ビューの帯
bdf_play_part(renderer, hash, scale, &canvas, &err)         Object パート 1 つ（シートのタイル）
```

**キャンバスに来るもの**。2D ライブラリがどれも名前を持っているものだけである。

| 関数 | 内容 |
|---|---|
| `save` `restore` `transform` `clip` | キャンバスが持つ状態は変換とクリップだけ |
| `fill` `stroke` | パスと、その描画のスタイル全部（色またはペイント、alpha、合成、影、線） |
| `image` | デコード済みの画像（premultiplied RGBA）の一部を矩形に |
| `begin_layer` `end_layer` | グループ。透明な別のキャンバスに描いて、alpha と合成つきで 1 枚として重ねる |
| `text`（任意） | 文字列とフォント。NULL なら（または 0 を返せば）libbdf がグリフの輪郭を `fill`/`stroke` に渡す |

**状態はプレイヤーが持つ**。塗りと線のスタイル、alpha、合成、影、線幅と破線、フォントは描画のたびにスタイルとして渡す。キャンバスに `setFillStyle` のような関数を並べなかったのは、2D ライブラリごとに状態のモデルが違う（cairo はソースが 1 つ、Core Graphics は塗りと線で別、Skia は SkPaint を毎回渡す）ので、どれに合わせても残りが翻訳を要るからで、毎回全部渡せばどれも素直に書ける。変換とクリップだけはキャンバスの状態にした。これはどのライブラリにも save/restore があり、クリップは取り消せないのが普通だからである。

**パス**は move、line、quad、cubic、close だけにして渡す。矩形、楕円、角丸、arcTo はプレイヤーがラスタライザと同じ式で 3 次曲線に直す。点だけの部分パスは渡さない（ラスタライザも何も描かず、2D ライブラリによって点になったりならなかったりする）。何もないパスは `clip` にだけ渡り、全部を切り取る意味になる。

**画像**はレンダラがデコードしたものを渡す。`id` が 0 でなければ、レンダラが生きている間、同じ `id` は同じ画素なので、アダプタは自分の形式（`cairo_surface_t`、`CGImage`）に直したものを `id` で覚えておける。アダプタをレンダラごとに作る（`bdf_cairo_new(renderer)`）のはこのためである。

**ソフトマスク**は 2D ライブラリに共通の言い方がない（Core Graphics はクリップ マスク、cairo は `cairo_mask`、Canvas 2D は destination-in）。プレイヤーはマスクの中身をラスタライザで描き、輝度かアルファを 1 枚の画像にして、合成 `BDF_BLEND_DESTINATION_IN` の `image` として渡す。グループがそれまでに描いたものがその画像で掛けられる。マスクの解像度は `scale`（ページの 1 単位が何ピクセルか）で決まるので、拡大して描くときは呼び出し側がその倍率を渡す。

**テキスト**は既定ではグリフの輪郭で渡る。配置はラスタライザのもの（§15）なので、どのアダプタでも `bdf_render_page` と同じ位置に同じ形が出る。ネイティブのテキスト API で描きたいキャンバスは `text` を実装する。文字列、基準点、作成時の幅、揃え、ベースライン、方向、字間、FONT 命令のフォント、文書が持つフォントなら sfnt のバイト列（WOFF2 は展開済み）が渡る。描けなければ 0 を返せば、その文字列だけ輪郭に戻る。

**影**は Canvas 2D と同じく、変換に関係なくページの単位で渡す。ぼかしの形はライブラリごとに違うので、影のあるページは基準の絵と同じにはならない。cairo には影がないので、cairo のアダプタは描かない。

**パターンの画素**。ラスタライザは SMOOTHING の指定に関係なくパターンを双一次で補間し、繰り返す軸では反対側の画素と混ぜ、繰り返さない軸では端の画素を延ばしてセルで切る。アダプタはこれに合わせる。cairo は軸ごとの繰り返しを言えないので、繰り返さない軸の端を 1 画素ずつ足した画像を作って帯でクリップする。Core Graphics の `CGContextDrawTiledImage` は拡大しても補間しないので、見えているセルが少なければ、周りに 1 画素足した画像をセルごとに描く（多ければタイルに任せる。そのときは 1 セルが小さく、補間の差は見えない）。Core Graphics の拡大の補間は双一次より移り変わりが急で、これは合わせられない。

**アダプタの置き場所**。ヘッダは `include/bdf/bdf_<名前>.h`、ソースは `adapters/<名前>/`、CMake のオプション `BDF_CAIRO`、`BDF_COREGRAPHICS`、`BDF_QT`、`BDF_SKIA` で静的ライブラリ `bdf::cairo`、`bdf::coregraphics`、`bdf::qt`、`bdf::skia` になる。ソース 1 つとヘッダ 1 つなので、単一ヘッダの `bdf.h` と一緒に自分のビルドに足すだけでも使える。

**4 つのアダプタの違い**。

| | cairo | Core Graphics | QPainter | Skia |
|---|---|---|---|---|
| 言語 | C | C | C++ | C++ |
| グループ | `push_group` | 透明レイヤー | 自前（別の `QImage` に描いて重ねる） | `saveLayer` |
| 図形の外まで及ぶ合成（copy、source-in など） | `copy` だけ図形の中のみ | そのまま | 別の画像に描いてから全体を合成 | レイヤーに描いて合成（Chrome と同じ） |
| hue・saturation・color・luminosity | ある | ある | ない（source-over で描く） | ある |
| 影 | ない | ある | ない | ある（画像フィルタ） |
| 円錐グラデーション | メッシュで近似 | 扇形で近似 | `QConicalGradient`（向きが逆なので反転） | `MakeSweep` |
| 片方の軸だけ繰り返すパターン | 端を足した画像と帯のクリップ | セルごとに描く | 端を足した画像と帯のクリップ | 軸ごとのタイル モード |

QPainter と Skia のアダプタは、C++ の例外を C のコアの中を通さない。キャンバスの関数が例外に会ったら印を付け、以後の関数は何もせず、描画はメモリ不足として終わる（ペインタとキャンバスは元の状態に戻す）。Skia は公式のリリースもパッケージも持たず API がマイルストーンごとに変わるので、アダプタはマイルストーン 124 に対して書いてあり、`BDF_SKIA_DIR` で Skia の場所を受け取る。CI は Aseprite が自分のビルド用に公開している Skia のビルドを使う（ハッシュ固定）。

**検証**。

- `tests/test_canvas.c`: 呼ばれたことを書き留めるキャンバスで、手で組んだページの呼び出し列を確かめる（状態の保存と復元、スタイル、画像の `id`、レイヤー、マスクの画素、テキストの 3 通り）。ライブラリと単一ヘッダの両方で走る。
- `adapters/<名前>/compare_<名前>`: 同じページをラスタライザとアダプタで描いて比べる。別のライブラリのアンチエイリアスと曲線で描くので同じ絵にはならず、バイトの差の平均と、64 を超えて違う画素の割合で見る。引数なしなら内蔵のページ（図形、線、グラデーション、画像とパターン、グループと合成、マスク、テキスト、ぼかさない影）を比べ、これが ctest の `adapter-<名前>` になる。文書を渡せばそのページを比べる。bdf の testdata の 239 ページは、cairo も Core Graphics も平均の差が 255 分の 0.7 以下（6 色だけの小さい画像の 1 ページが 1.2）で、離れたページはない。

## 17. SVG 画像

画像パートには SVG も入る（Markdown や HTML、EPUB の図、draw.io の書き出しなど）。ビューアはブラウザに描かせるが、参照実装のラスタライザはブラウザを持たないので、**プレビューで出会う範囲の SVG を自分で描く小さなレンダラ**を持っている。libbdf はそれを移植した。librsvg や resvg は使わない。理由は画像のデコーダ（§14）と同じで、別の実装では同じ絵にならず、依存も増える。

| ファイル | Go の対応 | 内容 |
|---|---|---|
| `svg_xml.c` | `tinygodriver` の `encoding/xmlro`、`internal/xmltree` | 寛容な XML の読み手（HTML の実体参照と空要素、DOCTYPE の実体、深さと実体展開の上限） |
| `svg_doc.c` | `image/svg` の `svg.go` | 要素の木、id の表、属性（名前空間の接頭辞を外す、`xlink:href` は `href`） |
| `svg_css.c` | `css.go` | `<style>` のセレクタと宣言、詳細度と順序での適用 |
| `svg_value.c`、`svg_float.c`、`svg_str.c` | `value.go`、`color.go`、`strconv.ParseFloat` | 数値、長さ、変換行列、色。10 進から倍精度への変換は正しく丸める自前のもの（`strtod` はロケールに左右され、実装によって丸めが違う） |
| `rsvg.c` | `raster/imagebdf` の `svg.go`、`svgpath.go` | 描画: 継承するスタイル、ビューポート、図形と `path`、塗りと線、グラデーション、クリップ、テキスト、埋め込み画像、ラスタの管理 |

**描くもの**。`rect`・`circle`・`ellipse`・`line`・`polyline`・`polygon`・`path`（全コマンド、楕円弧）、塗りと線（破線、端と継ぎ目）、線形と放射のグラデーション（`href` の継承、`gradientUnits`、`gradientTransform`）、`transform`、`g`・`a`・`switch`、`use` と `symbol`、入れ子の `svg`（`viewBox` と `preserveAspectRatio`）、`clipPath`、要素の `opacity`（別の面に描いて重ねる）、`text` と `tspan`（§15 のフォントとレイアウト。`bdf_fonts` のフォントを使う）、`image` の `data:` URL（ビットマップと SVG。SVG の中の SVG は 4 段まで）。

**描かないもの**。マスク、フィルタ、パターン、マーカー。使われていれば警告を出す（「SVG masks are not applied」など）。外部ファイルへのリンクの画像も描かない。これは参照実装と同じ。

**ラスタにしてから描く**。SVG 画像は、表示される倍率に合わせたラスタ（透明な背景の RGBA）に一度描き、あとは普通の画像と同じに扱う（一部を描く、パターンにする、縮小コピーを使う）。倍率は √2 の冪に切り上げるので、少し拡大しただけでは描き直さず、最大でも 4096² の 2 倍の画素で止まる（`BDF_MAX_SVG_RASTER_PIXELS` で下げられる）。ラスタはレンダラが持つデコード済み画像の仲間で、同じ上限（§14）で古いものから手放す。`path` の解析結果と埋め込み画像は文書ごとに覚えておき、`use` で何度描かれても一度しか作らない。キャンバスのプレイヤー（§16）にも SVG 画像はこのラスタとして渡る。

**同じ絵のために**。

- 倍率の `math.Pow(2, step/2)` は、Go の `Pow` が奇数の step で返す値（1 と −3 以下では √2 の倍数、それ以外では 1 ulp 小さい）をそのまま表にした。
- フォント ウェイトの `strconv.Atoi` と、その後の整数演算の桁あふれ（`bolder` で 300 を足す）まで Go と同じにしてある。
- `data:` URL の base64 は Go のデコーダの受理・拒否（改行の読み飛ばし、パディングなしの再試行、余りビットを見ない）を再現した。

**参照実装と違えたところ**。

1. **文字コード**。参照実装は `x/net/html/charset` の 228 のラベルを全部読む。libbdf が復号するのは UTF-8、UTF-16（BOM か宣言）、それに ISO-8859-1・US-ASCII・windows-1252（参照実装と同じく、どれも windows-1252 として読む）。それ以外のラベル（`shift_jis`、`euc-jp`、`gbk`、`iso-8859-2` など 196 個）は、宣言より後ろが ASCII だけなら読める（参照実装のデコーダも ASCII をそのまま通すので、結果は同じ）。ASCII 以外を含むときと、`replacement` 系の 6 ラベルは読まない。
2. **読み手の上限**。入力は 128 MiB まで。スタイル シートが要素ごとに持たせる宣言は 4,194,304 個まで（参照実装は要素ごとに map を作るので、メモリと時間をそのまま使う）。

これに当たる SVG は「an SVG image cannot be read」の警告になり、その画像だけが描かれない。どれも libbdf が断って参照実装が読む文書で、**読めた文書の木が違うものは知られていない**。

**移植で見つかって参照実装が直したもの**。次の 4 つは、移植の時点では参照実装が止まるか落ちるかしていて、libbdf だけが別の振る舞いをしていた。bdf 0.1.6 の後で参照実装が直り、いまは両者が同じである。

- `path` の `Z` の後にコマンド以外が来たとき（`M0 0Z5`）。参照実装は `Z` を読み直し続けて終わらなかった。いまはどちらもそこでパスの読み取りを終える。
- SVG 画像のパターンでラスタを置く余地がないとき。参照実装は nil を参照してページごと失敗した。いまはどちらもそのパターンを塗らない。
- スタイル規則のセレクタが結合子だけのとき（`<style>> {a:b}</style>`）。参照実装は panic し、libbdf はその SVG を読めないものとしていた。いまはどちらも、そのセレクタが何も選ばないものとして扱い、ほかの規則は効く。
- ラスタの倍率。参照実装は、作ったラスタには「幅（整数の画素）÷ 画像の幅」を、保持していたラスタには求めた √2 の冪を返していたので、同じページの 2 回目の描画や、別のページの後の描画がわずかに違った（libbdf はそれも写していた）。いまはどちらも常に前者を返し、何度描いても同じ画素になる。

**tinygodriver 1.3.5 への追随**。XML の読み手の元である `encoding/xmlro` が 1.3.5 で変わり、libbdf も同じ規則にした。

- XML 宣言として読むのは、ルート要素より前にある最初の `<?xml ?>` だけ。それ以外の `<?xml ?>` はただの処理命令で、文字コードを切り替えない。以前は文書の途中や最後にあっても宣言として読まれた。
- DOCTYPE はルート要素より前に 1 つだけ。ルート要素の後の DOCTYPE と 2 つ目の DOCTYPE は構文エラーになり、その SVG は読めない。
- 実体の展開で増える量は文書全体で合計して数え、バッファの上限（`MaxBufferBytes`）を超えたところで止める。以前の参照実装は事前に数えていて、別の文字コードを宣言する XML 宣言より前に DOCTYPE がある文書を見落とした。libbdf はそこだけ自前の 1 MiB の上限で止めていたが、参照実装が塞いだので外した。これで「libbdf だけが断る」実体の文書は無くなった。
- 宣言された実体は名前順に並べて二分探索で引く（同じ名前は先に宣言したものが勝つ）。実体の名前は 64 バイトまで数える。

追随の後、壊した文書 240,000 と作った文書 300,000 を amd64 で読み比べて、食い違いは 0。

**読み手が再現していること**。参照実装の癖のうち、木や値に出るものはそのまま写した。終了タグは名前ではなく名前の 32 ビット FNV-1a で開始タグと突き合わせる（`</liquid>` が `<costarring>` を閉じる）。`#text` という名前の要素はテキストの節として扱う。ルート要素が閉じた後の要素は木に入らないが、その id は表に入り、`style` はスタイル シートになる。`strings.ToLower` は Unicode の小文字化なので `PİNK` は色の pink、`1İN` は 1 インチ。数値は `strconv.ParseFloat` の移植（`readFloat`、`uscale.go` の桁合わせ、800 桁の 10 進へのフォールバック）で、指数の桁を読み切らないところや、800 桁を超える数の誤った丸めまで同じになる。参照実装で入力の 2 乗の時間がかかる箇所（クラスの重複除去）は、前回の答えを覚えて同じ結果を線形時間で出す。`Unescape` と `BoundEntities` もそうだったが、tinygodriver 1.3.5 と bdf の修正で参照実装のほうが線形になった。

**検証**。描画は、testdata の全 249 ページ（SVG を含む 8 ページを含む）と、乱数で作った SVG 文書（`go/svgs.go`: 図形、パス データの全コマンドと書き方の揺れ、スタイル シート、グラデーション、クリップ、`use`、入れ子、テキスト、埋め込み画像、壊れた値）を両方で描いて、amd64 でバイト単位に一致。警告の内容と順序も比べている。

読み手は別のパッケージ `go/svgdoc` で確かめる。C の文書と参照実装の文書を同じテキストに書き出して（節の順、名前、属性、`Sheet`、id の指す先、警告、それに全属性値の `ParseNumber`・`ParseNumbers`・`ParseLength`・`ParseColor`・`ParseTransform` を float64 のビットで）、文字列として比べる。

| 対象 | 件数 | 食い違い |
|---|---|---|
| 作った文書（`TestGenerated`） | 800,000（うち SVG として読めるもの 541,698） | 0 |
| 壊した文書（`TestMutations`、amd64） | 360,000 | 0（libbdf だけが文字コードで断るものを除く） |
| 壊した文書（arm64） | 300,000 | 0 |

ほかに、文書 317 個を割り当てが 1 回ずつ失敗する条件で読み（8,413 通り、すべて `BDF_ERR_NOMEM` で漏れなし）、差分テストの 200,000 文書をサニタイザの下で読ませた。arm64 の Go は `x*y + z` を融合するので、変換行列と hsl の色をビットまで比べるのは amd64 だけ（§13）。表（10 の冪、Unicode 17 の小文字化、HTML の実体 252 個、ラベル 228 個、windows-1252、色名 148 個）は `go/gensvg` が Go 側から書き出す。

ファザーは 3 つ。`fuzz/svgdoc_fuzz.c` は読み手だけを、`fuzz/svg_fuzz.c` は読んでから描くところまでを libFuzzer で叩く。Go の `FuzzSVG`（`go/svgdoc`）は読み手を参照実装と突き合わせる差分ファザー。描画の差分ファザーは置いていない。移植の時点では上の `Z` の無限ループが参照実装にあり、生のバイト列を両方で描くと Go 側が止まらなかったためで、bdf 0.1.6 の後の版からは置ける。読み手の最終コードで、Go の差分ファザーを 20 分（3,040 万回）、libFuzzer を ASan と UBSan の下で 20 分（86.8 万回、入力ごとに既定の上限と小さい上限で 2 回読む）回して、食い違い、クラッシュ、リーク、タイムアウトはなかった。途中で Go のファザーが見つけた 2 件（`#text` という名前の要素、文書の最後にある別の文字コードの宣言）は `go/svgdoc/testdata/fuzz/` と `fuzz/regress/svgdoc/` に入れてある。
